题目：校园活动与通知聚合Agent

【项目简介】汇集校园讲座、竞赛、社团招新、教务通知等活动信息，支持按时间范围、类别查询，并解决"第X周周三""11.15"这类不统一的时间格式。

【基本要求】
① 手工整理至少20条活动数据，混入3种以上时间格式（如"第X周""11.15""周三下午"），字段自行设计；
② 编写时间解析工具，将"下周""本月""周三下午"等自然语言时间转为具体日期，用至少10个时间表达测试并记录准确率；
③ 支持全文检索、按类别筛选、按时间范围筛选三类查询；
④ 输出统一格式：活动名称、标准化时间、地点、类别、来源。

【进阶要求】
① 定时抓取脚本从校网自动获取活动数据，解析失败须记录日志并走人工确认；
② 兴趣匹配子Agent：用户自选标签，新活动入库后主动推送；
③ 待办提醒：用户说"提醒我参加XX"即存入长期记忆，到时间自动提醒。



用着舒服。界面布局合理，操作有引导，输出格式干净。边界 case 基本都处理了——范围外老实说不知道、工具异常能恢复。
文档。中等三份 + DEPLOY（怎么部署、常见坑）+ ANALYSIS（需求分析、用例、流程图）。
技术底线。至少 3 个工具或 2 个工具 + 1 条 RAG。HITL 审批至少一个场景。至少一个中间件。数据清洗过程有记录——不是你随便扔进去就行。

    项目源码（zip 打包）整个项目跑得起来的全部代码。解压后按 README 的步骤能直接跑起来，这是最低标准。打包前清理掉.env、__pycache__、node_modules、.venv这些垃圾，不然包又大又容易带出密钥。
    README.md（都要交）给陌生人看的说明书：项目是干什么的、小组谁做了哪部分、环境要求（Python 版本、依赖）、怎么启动（几条命令）、常见问题（依赖装不上、模型连不上怎么处理）。必须配至少一张运行效果截图，不然验收的人不知道项目长什么样。别人拿到包，第一件事就是看这个文件。
    DESIGN.md（中等及以上）给评审看的架构文档：整体架构图（哪个模块调哪个）、模块职责说明（每个文件/类是干什么的）、数据流说明（用户输入怎么走完整条链路）、关键技术选型（为什么用 Chroma 而不是别的、为什么用这个模型）。
    REQUIREMENTS.md（中等及以上）功能清单文档：功能列表（每个功能一句话说清楚）、用户使用场景（谁在什么情况下会用到这个功能）、功能优先级（哪些是核心功能、哪些是锦上添花）。相当于把课题表里的基本要求和进阶要求翻译成你的功能规划。
    DEPLOY.md（良好及以上）部署文档：怎么从零搭环境、依赖安装命令、常见坑（比如模型下载失败、端口被占用怎么处理）、配置说明（.env里每个变量是干什么的）。验收的人照着这个能在新机器上把项目跑起来。
    ANALYSIS.md（良好及以上）需求分析文档：需求分析（用户是谁、要解决什么问题）、用例描述（典型场景的输入输出流程）、流程图（核心功能的流程画出来）、边界情况分析（空输入、超长输入、工具挂了会怎样）。
    SUMMARY.md（优秀）复盘文档：踩了哪些坑、怎么解决的、当时为什么绕了弯路、如果再做一次会怎么改、后续还能加什么功能。这篇写得好不好，直接体现你是真做了还是抄的。
    .env.example（都要交）密钥和配置的样例文件：把用到的变量名列出来，值填假的或留空（API_KEY=这种），注释说明每个变量的用途。让验收的人知道该配什么，又不至于看到你真密钥。不用 API Key 的项目也要把模型地址、端口、路径这些配置项列全。注意：真.env不要提交。
    数据文件 + 清洗说明（良好及以上）你项目里用的数据（校园资料、书籍清单、词汇库等）+ 一份清洗说明文档：数据从哪来的、怎么收集的、做了哪些清洗处理（去重、格式统一、字段裁剪）、样本量多少。数据是项目的地基，要让人能复核你的数据靠不靠谱。
    测试用例 + 测试结果（都要交）你跑过的测试证据：测试输入（问了什么问题、传了什么数据）、预期结果、实际结果、结论（通过/失败）。可以是一份 Markdown 表格或测试脚本输出。及格至少 5 组核心流程用例，等级越高用例越全（中等以上要覆盖边界和异常场景）。答辩演示用的就是这批用例，提前准备好，别临场瞎试。
